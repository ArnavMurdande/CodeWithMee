`P0B-S1` fixed the identity, session, organization-membership and course-staff schema semantics in [ADR 0001](adr/0001-unified-identity-authorization.md). This is a design contract only: no database command ran, no source record changed, and MongoDB remains authoritative until the Phase 0C migration gates.

`P0B-S2` adds isolated Mongoose compatibility models for auth identities, sessions and single-use tokens plus nullable legacy `User.password`/`username` and explicit current role/status fields. No live collection or existing document was changed in this run. The adapter can copy a verified legacy bcrypt hash into an identity and upgrade it to Argon2id on successful login; Google identities never receive placeholder passwords. Phase 0C must inventory email collisions, migrate these collections into the normalized tables, verify counts/relationships, and retain the read-only Mongo snapshot for rollback.

`P0B-S3` adds isolated compatibility models for organizations, memberships, staff invitations and provider verification reviews. No live collection or document was changed. Public UUIDs, revisions, normalized invitation email, HMAC token hashes, unique active keys and explicit verification/membership states match the target service contract. The Mongoose adapter uses atomic single-document claims plus compensating cleanup for cross-document operations; Phase 0C must replace those compensations with PostgreSQL transactions and prove the last-active-owner, invitation-consumption and verification-decision invariants under concurrency.

`P0B-S4` performs no data migration. It retires legacy learner/company credential minting and legacy Company-backed provider/admin mutations at the HTTP boundary, maps protected legacy learner handlers to the current unified principal, and preserves a default-off local-only verification bridge for already-issued learner tokens. That bridge reloads current User status/role and cannot be configured in production. P0B-S5 removes its client need; P0C still owns record claims, parity and database cutover.

`P0B-S5` performs no data migration and does not copy any browser credential. Existing persistent browser tokens are intentionally not imported into the unified session model: the cutover requires a fresh sign-in. The web keeps only a short access token in module memory and obtains new access through the P0B-S2 rotating HttpOnly refresh-cookie family. Client package removal changed only the deterministic dependency lock; no user, session, organization or external-provider record was touched.

`P0B-S6` performs no live data migration. The compatibility schema adds a default `authorityRevision` to users plus internal platform-authority control and append-only authority-audit collections. First-superadmin bootstrap, role/status changes, session revocation, owner-role swaps, organization revision update and audit insert share one Mongo transaction; a standalone server returns `authority_transaction_unavailable` before mutation. Phase 0C must map revision locks and audit rows to PostgreSQL, seed no privileged user automatically, and preserve the one-shot bootstrap marker/provenance during cutover.

`P0C-S1` creates only the empty relational target baseline. The migration maps the Phase 0 identity, session, OAuth, organization, file metadata, authority, audit, idempotency, outbox/job, feature-flag and import-provenance contracts. PostgreSQL-only additions enforce partial uniqueness, file readiness/ownership, immutable audit rows and a deferred exact-active-owner invariant. `prisma/migration-manifest.json` fixes schema/migration hashes and byte counts. The explicit seed reconciles authorization definitions only and creates no user or superadmin. The Docker rehearsal contained synthetic integration rows only and was destroyed with its anonymous volume; MongoDB and `server/uploads` remain unchanged and authoritative pending P0C-S2 through P0C-S5.

`P0C-S2` adds no database migration and performs no target write. Its registry covers all 18 present Mongoose models. A live source may be opened only through separate migration environment values, exact database-name approval and server-disclosed read-only roles; the application `MONGO_URI` is never a fallback. Canonical exports use per-record AES-256-GCM authentication, collection/index-bound associated data, plaintext/ciphertext checksums and a keyed manifest. Reports contain only safe shapes, counts, hashes and HMAC fingerprints. Fixture ambiguities are quarantined, reset material is discarded, and all legacy challenge cases stay visible. The real upload rehearsal only hashed/stat-ed 43 unchanged files, then deleted its generated report; no live Mongo source/parity evidence exists yet.

`P0C-S3` adds no migration and does not reinterpret the legacy files. It implements the target file lifecycle against the existing baseline table and emits transactional outbox events for scan, ready, visibility and object-delete work. The PostgreSQL rehearsal used generated UUID principals and an in-memory object adapter; every row existed only in the disposable database. A future P0C-S4/P0C-S5 transfer must create owner-reviewed file records, copy by verified hash to opaque private keys, scan every object, retain the legacy source through rollback, and quarantine any filename-only identity guess.

`P0C-S4` adds the normalized relational destinations for every present legacy collection and embedded data family without implementing future product features early. The offline importer accepts only the authenticated snapshot, applies one source record per transaction, records checksums/fingerprints and continues after semantic quarantine. Transient credentials are not carried forward: sessions, verification/reset tokens and pending invitation tokens are invalidated; legacy company passwords are discarded; Google accounts without a provider subject require relinking. Paid courses without ISO currency, duplicate/invalid identity, dangling parents and ambiguous organization claims do not write domain targets. Course progress is explicitly a non-authoritative snapshot, cache queries are stored only as hashes, audit reasons are redacted into the protected source, and legacy challenge cases are all visible. Successful fixture import is not parity or cutover evidence.

`P0C-S5` adds no live authority change. The fourth additive migration preserves actor-session, request and occurrence metadata required by the PostgreSQL audit repository. The runtime remains Mongoose by default and rejects partial core or premature feature-domain PostgreSQL selection. The local report is HMAC-authenticated and contains only counts, warning codes, structural results and hashes; the intentionally ambiguous fixture permits only the standalone authority data check and blocks the atomic core cutover. A separate synthetic control path proved matching feature-flag activation and rollback inside the disposable database. The production sequence and retained-source deadline are fixed in `docs/runbooks/PERSISTENCE_CUTOVER.md`.

`P0C-S6` adds no schema or live data migration. The portable verifier exports a repeatable-read application snapshot, binds it to the manifest, compresses/encrypts/authenticates it and permits restore only into a distinct migrated target. The local drill restored every row, compared a complete re-export before commit and removed its exact restore database/archive. The file report is read-only and keyed; it cannot delete an orphan or infer a legacy owner. Mongo/Mongoose and local uploads remain retained because live parity, managed backups, provider object versions, rollback expiry and legal-hold evidence are unavailable. The normative procedure is `docs/runbooks/BACKUP_RESTORE_AND_LEGACY_RETIREMENT.md`.

`P0D-S4` adds only format metadata. Old Mongo notes have no `contentFormat` default and are therefore projected as legacy HTML to plaintext; new/explicit saves write `plain_text_v1`. PostgreSQL existing notes receive `legacy_html_v0` before the column default changes, so the migration never falsely classifies old bytes as safe plaintext. No automatic content rewrite, live database command or source mutation occurred.

`P0D-S6` adds crash-recovery ownership to the existing idempotency table only. The runtime stores the SHA-256 operation scope in `key`, never the raw request key or request body; actor/action/request digest plus a UUID lease control acquisition, replay, mismatch, in-progress and recovery. The audit table remains database-enforced append-only, while outbox delivery uses existing `job_runs` leases and terminal states. The sixth migration is checksum-pinned and Prisma-valid but was not applied because no newly authorized disposable PostgreSQL target was available; production operations therefore fail closed without PostgreSQL, and development memory adapters are not durability evidence.
